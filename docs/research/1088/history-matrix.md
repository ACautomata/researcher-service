## 2. 测试分层与 S 编号

#747 Testing Decisions 已定义 S1（信封级集成）/ S3（纯逻辑单测）。本工具新增两个形态，编号顺延；本表只约束**本工具测试**的标注，不修改 #747 原文（共识 Q8）：

| 编号 | 形态 | 说明 | 宿主可跑 |
|---|---|---|---|
| S1 | 信封级集成 | 既有约定：真临时 SQLite + 真 init.sql 建表 + 服务级断言 | 是 |
| S2 | 图级装配冒烟（新增） | 真 RunService + 真 LangGraph 图 + `ScriptedChatModel` 假 LLM + fakePrimitives；断言工具装配、身份路由、审批路由与错误回喂格式。**最小化**，不测 ReAct 循环本身 | 是 |
| S3 | 纯逻辑单测 | 既有约定：纯函数、零 IO | 是 |
| S4 | 工具端口级（新增） | 不经图，直调历史模块公共 `execute(context, request, budget, signal)` Interface，断言结果、书签、进度、部分成功、资源释放 | 是 |

测试接缝遵循 #1070「已确认测试接缝」与 #1071「装配侧验收」的硬门：

1. 权限、SQL 读取、历史版本和分页必须使用**真实临时 SQLite 与真实数据 Adapter**，不得全用 repository 替身掩盖过滤/事务错误。
2. Worker/进程实际终止、只读连接、取消与资源释放必须走**真实执行器**验证——不得以 fake executor 声称满足「5 秒实际终止」。
3. 装配侧验收用**可观察行为**（工具是否在图里、误调用是否被拒、错误如何回喂），不得只断言提示词包含某字符串。
4. 时钟、日志故障经 Interface 注入，便于验证 TTL、日志失败与预算边界。

## 5. 安全验收

### 5.1 schema 白名单契约测试（守「无 shell 执行面」红线，共识 Q4）

一条静态契约测试断言 `session_history` 工具的 zod schema 字段集合恰为白名单（operation/session_ids/title/time/query/case_sensitive/fields/context/targets/range/cursor 等以实施规格 schema 为准）。任何新增自由字符串命令字段、exec 类字段或 ownerId 类字段都会使该测试失败。断言双重含义：(a) 无任意 shell/SQL 入口；(b) 无身份绕过字段（C14/P1/G10）。

### 5.2 禁读目标表（表驱动，共识 Q5）

单一参数化测试：每行一个禁读目标，统一断言——(a) 同形「该会话不可读取」响应；(b) 不含标题/owner/内容/任何存在性推断信息；(c) 其余合法目标结果不受影响（部分成功语义）；(d) 普通搜索中该目标零出现（目录/命中/计数/续读）。

| 行 | 场景 | fixture 构造 |
|---|---|---|
| SEC-1 | 他人会话 | 不同 ownerId 的含消息会话 |
| SEC-2 | 不存在会话 | 合法格式的随机 ID |
| SEC-3 | 已物理删除 | 删除后的 ID |
| SEC-4 | archivedAt 软删存档 | 归档行 |
| SEC-5 | teammate 隐藏会话 | isTeammate=true |
| SEC-6 | rewind 废弃分支消息 | 回退后不可见路径消息 |
| SEC-7 | admin 请求他人会话 | admin 身份 + 他人会话 |
| SEC-8 | 显式当前会话 | 当前会话 ID——**期望专门提示**（非同形不可读），单独断言（P7） |

独立单测：并发删除 → 历史版本失效（局部失效、其他目标继续）——归 O16/P11/M7 组合用例。

## 6. 预算验收方式（共识 Q9）

- #1069 全部数字上限以配置/参数注入测试，不硬编码断言具体数值；
- 每条预算断言行为三要素：**超限即停**（不超额交付）、**状态按协议**（more/stopped/错误分类，不伪装完成或空历史）、**续读/重试指引正确**；
- 实施规格调整数值时，本矩阵测试无需修改。

## 7. 宿主 / 容器划分与人工冒烟（共识 Q6）

- 自动化：全部宿主 vitest、零 Docker——工具只读 SQLite，不触容器编排。
- 容器化 dev 栈**人工冒烟（非门禁）**，发布前执行一次并记录进实施票：
  1. `docker compose -f deploy/docker-compose.dev.yml up -d --build`（发消息需 `LLM_API_KEY`）；
  2. 建两个会话各发数条消息，删除或归档其一；
  3. 在存活会话中让 leader 检索历史，验证：命中存活会话、被删会话不可见、出处引用可读、额度/续读提示正常。
