# ADR 0001：持久化凭证的应用层加密

## 状态

已接受。

## 背景

`containers.Instance.token`、`chat.Pairing.private_key_pem` 和
`chat.Pairing.device_token` 是数据库中持久化的凭证。它们不应依赖 API 或 admin 的
展示限制来保证机密性。

## 决策

### 算法与密文格式

使用 `cryptography` 提供的 AES-256-GCM。每次写入使用新的 96-bit nonce；密文编码为
`enc:v1:<base64url(nonce || ciphertext || tag)>`。GCM 提供机密性和认证，版本前缀让
以后更换格式或算法时可以显式迁移，而非猜测密文含义。

### 密钥来源

使用独立的 `CREDENTIAL_ENCRYPTION_KEYS` 环境变量，不从 `DJANGO_SECRET_KEY` 派生。
它是按优先级排序的、逗号分隔的 base64url 编码 32 字节密钥：第一把用于新写入，后续
密钥仅用于解密历史密文。两类密钥的轮换、泄露影响和职责不同，必须独立管理。

### 生产 fail-fast

生产 settings 在启动期解析该变量。变量缺失、为空、含非法 base64url、解码后长度不是
32 字节或含重复密钥时，应用拒绝启动；绝不回退为明文或内置默认密钥。

### 轮换

轮换时先将新密钥置于首位、保留旧密钥在列表中，因而现有数据仍可读取且新数据立即用
新密钥写入。后续 #57 将提供重加密命令和运维流程；确认所有密文均已重写后，旧密钥才能
从环境变量移除。

## 后果

#54 只提供与模型无关的加解密基元和生产配置。#55 将通过 `EncryptedTextField` 采用该
基元，实现新写加密与旧明文的临时读兼容；#56 迁移并移除兼容；#57 完成重加密和旧密钥
下线。
