# 会话删除修复 + 附件发送(图片/音频/视频)

## Problem Statement

当前面板存在两个影响日常使用的缺陷:

1. **删除会话"点了没反应"**:用户点击会话侧栏的 ✕、确认后,会话没有被删除,反馈微弱到像"没反应"。删除实现已存在(经 WS 隧道直发网关 `sessions.delete`,PR#370 修复过 archivedOnly 与 operator.admin scope 两轮 bug),但错误提示走顶部小字 bar,可感知性差,且确认框文案「网关会先归档(可恢复)再删除」与实际硬删除行为不符——现状会让用户以为会话"还留着/可恢复",与真实语义矛盾。
2. **无法发送图片/音频/视频**:composer 只能发纯文本,没有附件采集入口(粘贴/拖拽/文件选择),`chat.send` 也不携带附件,历史消息里的非文本内容块被直接丢弃(渲染层遇非 text 块返回空)。

## Solution

1. **删除反馈与文案修正**:删除确认文案改为明示「直接删除、不可恢复」;删除失败改为醒目的 toast 提示(替换/叠加顶部小字 bar),删除成功保留 toast。真实网关行为需闭环验证(ADR 0006 实测项 ③)。
2. **通用附件发送**:composer 支持粘贴、拖拽、文件选择三种方式采集附件,发送前以缩略图列表预览(可逐个移除);图片经前端压缩(最长边 1280,JPEG/WebP);非图片附件限体积 ≤700KB,超限拒发并提示;附件经 WS 隧道随 `chat.send` 内联发送(官方 `attachments` 字段)。
3. **附件渲染**:历史消息与流式消息中的 image/audio/video 内容块全部渲染(修复当前丢弃非 text 块的问题)。

## User Stories

1. 作为面板用户,我想点击会话侧栏的删除按钮并确认后,会话被真正删除且不可恢复,以便清理不需要的历史对话。
2. 作为面板用户,我想删除失败时看到醒目的错误提示,以便知道我该重试或换一种方式处理。
3. 作为面板用户,我想删除当前正在对话的会话后停留在空聊天区,以便决定新建会话还是切换其他会话。
4. 作为面板用户,我想在确认删除时看到「直接删除、不可恢复」的文案,以便准确理解删除的后果。
5. 作为面板用户,我想通过粘贴图片(剪贴板)直接发送图片,以便快速分享截图。
6. 作为面板用户,我想通过拖拽图片/文件到输入区发送附件,以便用鼠标完成发送。
7. 作为面板用户,我想通过文件选择按钮挑选要发送的附件,以便精确控制发送内容。
8. 作为面板用户,我想在发送前看到附件预览条(缩略图列表 + 逐个移除),以便确认要发送的内容、移除误选的附件。
9. 作为面板用户,我想发送图片时图片被自动压缩到合理大小,以便图片能顺利通过面板隧道(1MiB 帧上限)送达 AI。
10. 作为面板用户,我想发送超过体积上限的附件时得到明确提示(「文件过大」),以便知道是体积问题而非故障。
11. 作为面板用户,我想发送音频/视频/文档等通用附件,以便与 AI 分享非图片内容。
12. 作为面板用户,我想在历史消息中看到自己发送的图片/附件渲染出来,以便确认发送成功、回看内容。
13. 作为面板用户,我想在 AI 回复中看到图片(如 browser 截图)、音频、视频渲染出来,以便直接查看 AI 工具产出的多媒体内容。
14. 作为面板用户,我想在流式对话中也能看到附件相关的内容块正常渲染,以便对话过程不丢内容。
15. 作为面板用户,我想纯图片消息(无文本)不影响对话发送,以便直接发图。
16. 作为面板用户,我想删除会话后审计日志(文本对话)不受影响,以便日志分析保持按文本语义进行。

## Implementation Decisions

### 删除分支

- **删除语义**:会话删除 = 硬删除,不可恢复;归档是未来功能(本次不做),UI 文案不得出现「归档/可恢复」字样。
- **删除通道**:保持现状——WS 隧道直发网关 `sessions.delete {key}`(不带 `archivedOnly`);服务端零改动(会话不存于控制面,6 张表无 Session 表;REST 代理面 #339 已作废)。
- **错误呈现**:删除失败由顶部小字 bar 改为醒目 toast(叠加或替换);定位并修复可能的静默吞错点。
- **删除当前会话**:允许;删后停留在空聊天区(空态视图 + 「新建会话」入口)。
- **真网关验证**:闭环 ADR 0006 实测项 ③——不带 `archivedOnly` 的删除在真实网关上是否成功、是否要求 `operator.admin`;若发现要求,核对现有 `OPERATOR_SCOPES`(已含 admin)是否满足。

### 附件分支

- **协议形态**:`chat.send` 携带官方 `attachments` 字段,`{type?, mimeType?, fileName?, content?, sizeBytes?, durationMs?, width?, height?}`;content 为自由形状(0 信任)。
- **采集**:粘贴(剪贴板图片)+ 拖拽(文件/图片)+ 文件选择按钮,三通道全支持。
- **预览条**:发送前缩略图列表 + 逐个移除 + 合计状态。
- **图片压缩**:canvas 降采样最长边 1280 + JPEG/WebP 压缩,发送前完成;压缩后仍超限则拒发。
- **体积上限**:非图片附件 ≤700KB(base64 后 <1MiB 隧道上限,留余量);超限拒发并提示「文件过大」。
- **渲染**:`extractMessageText` 遇非 text 块不再丢内容;image/audio/video 块分别渲染(图片 img、音频 audio、视频 video)。
- **审计**:纯图片消息(无文本)不落 `TextTraceLog`(保持现状,审计按文本语义)。
- **新增模块**:`attachments.ts` 纯函数模块——采集→压缩→体积校验→组装 `attachments[]` 数组。

### 服务端

- 零改动。隧道是字节管道,帧透传;`TUNNEL_MAX_PAYLOAD`(1MiB)与 `TUNNEL_SEND_BUDGET`(4MiB)维持不变(体积策略已适配该约束)。

## Testing Decisions

- **只测外部行为,不测实现细节**——测「删除后会话从列表消失 + toast 出现」「发送附件后 `chat.send` payload 含 attachments」「历史消息渲染出 image/audio/video」,不测内部状态。
- **测试模块**:
  - 高层 seam:`views/ChatView.test.ts`——删除完整流程(✕ → confirm → mock 网关 → 断言侧栏消失/当前会话删除后空态/toast),附件发送完整流程(粘贴/拖拽/选择 → 预览条 → 发送 → payload 断言)。
  - `chat/eventTranslate.test.ts`——历史消息 image/audio/video 块 → 附件渲染数据。
  - `chat/gatewayChat.test.ts`——`send()` 带 attachments → `chat.send` payload 形状。
  - **新 seam** `chat/attachments.test.ts`——压缩尺寸/体积校验/类型过滤/超限拒发。
- **先例**:上述测试文件均已存在,沿用其 vitest + 组件挂载 + mock 网关的模式。

## Out of Scope

- 归档功能(保留数据、移出列表)——未来功能,本次不做。
- 网关侧 `sessions.files.set` 上传通道(大文件另路)——本次不做,大附件策略为限体积。
- 调大隧道 `TUNNEL_MAX_PAYLOAD` / `TUNNEL_SEND_BUDGET`——维持防滥用预算。
- 音频/视频的播放器级体验(时长、进度、流式)——仅基础渲染(audio/video 标签)。
- 服务端任何改动(审计日志、REST 代理)。
- 非 image/audio/video 类型附件块的渲染(文档等仅发送,渲染层不处理)。

## Further Notes

- 删除链路代码已存在(PR#370 修复过两轮 bug),活的缺口是**错误反馈 + 文案 + 真网关验证**,不是从零实现。
- 附件体积预算与隧道 1MiB 帧上限的关系是硬约束,任何调整须重新核算 base64 膨胀系数。
- `useChatConnection.ts:924` 注释「网关先写压缩归档(可恢复)再删」与实现不符,属留档误导,随文案修正一并清理。
